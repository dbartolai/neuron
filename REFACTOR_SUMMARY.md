Transform Neuron from a code generator with guardrails into a **pedagogy-first Socratic tutor** with deterministic fallback behavior.

### **Fallback Behavior**

#### BEFORE: Model-Dependent (Unreliable)
```python
# levels.py line 46-47 (Writing Level 0)
"FALLBACK: If the user asks for code, refuse and suggest asking staff."
```
**Problems:**
- ❌ This is an **instruction**, not enforcement
- ❌ Model can ignore it (no code catches violations)
- ❌ Generic rejection: "I can't help with that"
- ❌ No pedagogical redirection

**Example Response (OLD):**
```
I can't provide code at this level. Please ask your instructor 
or raise your writing level.
```
*Generic, unhelpful, discouraging*

#### AFTER: Code-Generated (Deterministic)
```python
# fallback_service.py
violation_type = infer_violation_type(violations, prompt)
fallback = generate_fallback(
    violation_type=CODE_GENERATION_DENIED,
    thread_type="writing",
    level_index=0,
    student_prompt="Write a sort function",
    violations=[...]
)
```
**Benefits:**
- ✅ **Deterministic**: Generated by Python, not LLM
- ✅ **Pedagogical**: Explains restriction + offers help
- ✅ **Actionable**: Suggests concrete next steps
- ✅ **Encouraging**: Frames as learning opportunity

**Example Response (NEW):**
```markdown
## Understanding Your Request
I understand you'd like me to generate code for sorting.

At your current **writing level 0**, I cannot provide actual code 
implementations. This restriction helps you build problem-solving 
skills by working through the logic yourself.

## What I Can Help With
However, I can help you in these ways:
- Explain the **concepts** behind sorting in plain language
- Discuss **algorithmic approaches** at a high level
- Answer questions about **how sorting works** conceptually
- Clarify any **course materials** related to this topic

## Suggested Next Steps
To move forward:
1. **Ask me**: 'Can you explain how sorting works conceptually?'
2. **Try**: Sketch out your approach in words (no code yet)
3. **Check with me**: Share your verbal plan and I'll help refine it

*If you need code assistance, ask your instructor about raising 
your writing level, or use the Testing/Debugging threads at higher levels.*
```
*Specific, helpful, encouraging*

### **System Prompt Structure**

#### BEFORE: Ad-Hoc Instructions
```python
# chat_service.py line 117-121 (OLD)

    "All responses must be valid GitHub-Flavored Markdown.\n"
    "Do not emit HTML.\n"

```
**Problems:**
- ❌ Tutor identity not stated
- ❌ Teaching approach not specified
- ❌ No required response structure
- ❌ Formatting rules, not pedagogy

#### AFTER: Complete Teaching Contract
```python
# chat_service.py (NEW)
system = build_system_prompt(level_guardrails=guardrails)
```

Expands to:
```
You are **ceria**, a Socratic coding tutor focused on teaching, not solving.

Your Core Purpose:
- Foster deep understanding through guided discovery
- Build problem-solving skills, not deliver solutions
- Encourage student agency and self-directed learning
- Make learning engaging, supportive, confidence-building

Your Teaching Philosophy:
- Students learn best by doing, not watching
- Struggle is productive when paired with strategic support
- Conceptual understanding must precede implementation
- Every interaction is a teaching moment

---

Teaching Approach (Always Follow):
1. UNDERSTAND FIRST
   - Restate the student's question
   - Ask clarifying questions if ambiguous
   - Identify the learning gap

2. TEACH, DON'T TELL
   - Explain the "why" before "how"
   - Use analogies and examples
   - Connect to prior knowledge
   - Break into manageable steps

3. GUIDE DISCOVERY
   - Ask Socratic questions
   - Provide hints, not complete solutions
   - Encourage student proposals
   - Validate correct reasoning

4. EMPOWER ACTION
   - Suggest concrete next steps
   - Explain how to verify work
   - Anticipate common pitfalls
   - Build confidence

5. METACOGNITIVE REFLECTION
   - Help students reflect on process
   - Point out effective strategies
   - Generalize approaches

---

Your responses MUST follow this structure:

## Understanding Your Question
[Restate what the student is asking]

## Teaching Response
[Teaching content adapted to level constraints]

## Next Steps for You
- [Action 1: What to try next]
- [Action 2: How to verify]
- [Optional: Extension]

---

[CORE_PRINCIPLES]
[LEVEL-SPECIFIC GUARDRAILS]
```

**Benefits:**
- ✅ **Explicit Tutor Identity**: Model knows its purpose
- ✅ **Structured Pedagogy**: 5-step teaching framework
- ✅ **Required Output Format**: Consistent structure
- ✅ **Single Source of Truth**: One place to update

### What Still Needs Work
1. **Response Validation** ⏳
   - Still relies on LLM judges (slow, expensive)
   - Only 1 retry attempt
   - Vague corrective messages

2. **Level Policies** ⏳
   - Still 912 lines of strings
   - Duplication across rule types
   - Hard to query/validate
   - **Plan:** Dataclass-based policies

3. **Structured Outputs** ⏳
   - Free-text responses (hard to validate)
   - Inconsistent formatting
   - Can't programmatically extract sections
   - **Plan:** JSON schema or Markdown parser

4. **Testing** ⏳
   - No automated test suite yet
   - No metrics dashboard
   - Manual testing only
   - **Plan:** 140-test automated suite

## 🎓 Key Learnings

### What Worked Well
1. **Deterministic Fallbacks**: Replacing model instructions with code generation was 100% effective
2. **Single Contract**: Having one source of truth eliminated drift and inconsistency
3. **Pedagogical Focus**: Making tutor identity explicit improved response quality
4. **Incremental Refactor**: Phased approach allowed testing without breaking production

### What We'd Do Differently
1. **Start with Testing**: Should have written tests BEFORE refactoring
2. **Structured Outputs First**: Would have been easier to validate with structure enforced from day 1
3. **Metrics Earlier**: Would have liked baseline metrics before changes

---

## 💡 Recommendations

### For Future Prompt Engineering
1. **Never Rely on Model Instructions Alone**: Always have code-based fallbacks
2. **Explicit is Better Than Implicit**: State identity, purpose, and structure clearly
3. **Structure Everything**: Free-text outputs are hard to validate and iterate on
4. **Test Adversarially**: Assume students will try to bypass guardrails
5. **Pedagogy > Convenience**: It's better to say "I can't, but here's what I can" than to give the wrong help

### For Production Deployment
1. **Phase Rollout**: Deploy Phase 1-2 first, monitor, then continue
2. **Metrics Dashboard**: Track fallback rates, retry rates, satisfaction by level
3. **Feedback Loop**: Regular check-ins with instructors and students
4. **A/B Testing**: Test prompt variations with control groups
5. **Graceful Degradation**: Always have a safe fallback, even for fallbacks

## 🙏 Acknowledgments

This refactor addresses fundamental issues in LLM-based tutoring systems:
- **Guardrails as suggestions** vs **guardrails as enforcement**
- **Generic rejection** vs **pedagogical redirection**
- **Implicit teaching** vs **explicit teaching contracts**
- **Hope-based validation** vs **deterministic validation**

The solution combines:
- Software engineering best practices (separation of concerns, single source of truth)
- Pedagogical principles (Socratic method, scaffolding, student agency)
- Practical guardrails (multi-layer validation, deterministic fallbacks)

**Result:** A tutoring system that reliably teaches, doesn't just generate code.
